# 혼잡 시간창 정확 재패킹 (window-LNS) — 실제 엔진, Z1 개선 0

## 목적
스케줄/배정/slack 축이 모두 포화 확인됨. 남은 유일 레버 "더 촘촘한 배치"를 직접 검증:
peak 혼잡 창의 블록들만 골라 위치를 실제 bigleft 배치기로 다시 짜서 더 밀어넣기 → Z1↓?

## 방법 (`run_window.py`, 실제 submit_v34 엔진, python3.12)
1. rank bigleft 해(Z1=2359) 재구성.
2. 대기 카운트 최대 시각 pk = peak 창 중심. 창 [pk±WIN].
3. 창의 블록을 **destroy**, 나머지는 현재 좌표로 **freeze**(엔진에 로드 → 재배치는 이들과
   겹칠 수 없음, 해 항상 feasible 유지).
4. destroy된 블록을 **bigleft 스코어링 그대로**(find_best_placement 아님 — positioning
   22% 열세) frozen-aware free-span으로 재배치. dispatch 순서를 25종(orig/rank/edd/area/
   rel + rank섭동 20) 시도해 창-지각 최소 채택. 전체 Z1 개선 + feasible 일 때만 확정.

## 결과 (prob_38, 각 6분)

| 변형 | peak | 창 블록 |A| | 창-지각 시작→최선 | 전체 Z1 | Δ |
|---|---|---|---|---|---|
| 창에 '진입'하는 블록 | @47 | 60 | 209 → 209 | 2359 | **0** |
| 창에 '존재'하는 블록(최대자유) | @47 | 70 | 303 → 303 | 2359 | **0** |

**25개 순서 × 60~70블록 정확 재배치로도 창-지각을 1도 못 줄임.** frozen 경계 안에서
활성 블록들을 어떻게 재배열해도 공간이 안 남음 = 그 창은 수요>용량으로 진짜 포화.

## 종합 결론 — 2359는 이 엔진의 기하 패킹 바닥
네 축을 전부 실제 엔진에서 소진, 모두 rank(2359) 개선 실패:
| 축 | 시도 | 결과 |
|---|---|---|
| order | area/width cumulative, eff스윕, 사전식 big-early, tiebreak (7종) | 잘해야 tie |
| bay 배정 | CP-SAT area/width | 악화 |
| slack 재분배 | 대기창 여유블록 제거→조기착석 | 이득 0 |
| **window 재패킹** | peak창 60~70블록 정확 재배치 25순서 | **이득 0** |

→ 고밀도 인스턴스의 지각은 **구조적**: peak 시각에 공간 수요가 용량을 초과 → 대기 불가피.
   현재 bigleft 엔진의 배치 품질 하에서 2359는 사실상 달성 가능한 바닥.
   (참고: area-완화 LB ~1645는 기하를 무시한 낙관 하한이라 도달 불가로 판단.)

## 남는 가능성 (불확실, 고비용)
2359를 더 깨려면 bigleft보다 **근본적으로 촘촘한 배치**가 필요:
- 진짜 정확 불규칙 nesting(NFP 기반 MIP/CP)로 전역 재패킹 — 250 불규칙다각형+크레인+시간
  이라 연구급 난도, 페이오프 불확실(본 window-LNS가 국소 프록시로 이미 0).
- 크레인 통로 공유 co-placement(진입/이탈 코리도 정렬로 유효밀도↑) — 특화 기하개선.
본 실험 근거상 헤드룸은 작을 것으로 추정. 스케줄측 튜닝은 중단 권고(수확체감).
