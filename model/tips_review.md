# 비트 팩킹 팁 3가지 — 우리 문제 기준 검토

결론 요약: **팁1·팁3은 "탐색/열생성 pricing 엔진"용으로 유용**(단 조건부 수정 필요),
**팁2(크레인 선형화)는 우리 문제에선 틀린 식** — 고쳐야 한다.

전제: 팁1·3은 MIP 자체가 아니라 **고속 feasibility 검사(휴리스틱/열생성 pricing)** 도구다.
"수리계획으로 최적해"의 코어는 여전히 MIP(집합분할)이고, 팁1·3은 그 MIP에 **좋은 열을
빠르게 공급**하는 가속기로 붙일 때 진가가 난다.

---

## 팁1. 시간축을 uint64 하나에 팩킹 + Numba  →  좋음, 단 2가지 수정 필수

좋은 발상(셀→시간 비트필드는 "이 발자국이 [t_in,t_out) 동안 들어갈까?" 질의에 최적).
그러나 우리 데이터에서 두 곳이 깨진다:

1. **시간축 64 초과.** 학습 40개 중 **34개가 due_date>63**(최대 150, release 최대 141).
   지연까지 감안하면 지평은 더 길다. → 단일 `uint64`로는 85% 인스턴스가 안 됨.
   해법: 셀마다 **uint64 여러 워드(word) 배열**로 비트셋 확장(예: 지평 160 → 워드 3개),
   또는 시간 원점 이동/롤링 윈도로 구간만 담기. Numba는 워드 배열에도 그대로 먹힌다.
2. **레이어 인덱스 누락.** 팁의 `grid[x,y]`(2D)는 레이어를 뭉갠다. 우리 문제의 핵심 이점은
   "서로 다른 레벨이면 top-view가 겹쳐도 됨"(문제 Figure 7a). K는 최대 4.
   → 격자는 반드시 `grid[x, y, layer]` (각 칸이 시간 비트필드)여야 한다. 안 그러면
   교차레벨 조밀배치를 스스로 버려 품질(=지연↓)을 깎아먹는다.

수정 후 결론: **열생성 pricing / 국소탐색의 feasibility 검사에 매우 유효.** MIP LP 안에는
못 들어가지만(비트AND는 비선형), pricing에서 "이 열이 실행가능한가"를 1ns급으로 판정해
좋은 열만 마스터문제에 넣는 용도로 이상적.

## 팁2. 크레인 선형화 `A_{x,y,t_in} + A_{x,y,t} ≤ 1 (∀t>t_in)`  →  **틀림. 고쳐야 함**

제안식의 두 가지 오류:

1. **"영구 금지" ≠ 크레인.** 크레인 제약은 *입·출고 그 순간*의 수직 통로만 비우면 된다.
   제안식은 한 번 (x,y)에 넣으면 **미래 모든 t에서 그 바닥을 영구 금지**한다. 그러나 블록이
   나간(EXIT) 뒤에는 그 (x,y)를 **재사용해야 정상**이다. 예: 블록 A가 [2,5) 점유 →
   t=10에 블록 B가 같은 (x,y) 사용은 합법인데, 제안식은 이를 금지한다. → 과잉제약, 최적성
   대량 손실(특히 지연↑).
2. **레이어 인덱스 없음.** 크레인 규칙은 "i의 l1 vs 남의 l2 (l2≥l1)"라는 **레벨 관계**다.
   평탄한 `A_{x,y,t}`엔 레벨이 없어 "같거나 위층"을 표현할 수 없다. 같은레벨 비겹침은 이미
   일반 팩킹(`sum≤1`)이 처리하므로, 크레인이 추가하는 것은 *입출고 순간의 위쪽 기둥*뿐이다.

**올바른 선형화(우리가 이미 쓰는 방식, bitmask_3d_approach §3.3):**
복셀 점유 이진 `o_{i,x,y,k,t}` 에 대해
```
(비겹침)   sum_i o_{i,x,y,k,t}  <= 1                      for all (x,y,k,t)
(크레인)   입고일 t=EN_i / 출고일 t=EX_i-1 에 한해, i의 점유 발자국 위 '수직 그림자'
           셀을 그 순간 점유에 더해(occ+) 같은 sum<=1 에 포함.
           즉 shadow_i = { (x,y,k') : (x,y,k) in occ_i, k'>=k } 를 EN_i, EX_i-1 에만 추가.
```
- 핵심: **"영구 금지"가 아니라 "그 순간의 위쪽 기둥만 청소"** + **레벨 인덱스 유지**.
- 이러면 크레인이 별도 부등식 없이 **set-packing 안에 정확·선형**으로 녹는다. Branch-and-
  bound도 이 형태를 좋아한다. (제안식처럼 O(cell×t^2)로 불어나지도 않는다.)

## 팁3. `~Grid` 반전으로 가용 스카이라인  →  유용, 단 3가지 단서

표준 비트보드 트릭. 후보 위치 열거를 벡터화하는 데 좋다. 그러나:

1. **지평 밖 비트 오염.** numpy `~`는 미사용 상위비트까지 1로 만든다 → 유효지평 마스크와
   AND해서 쓰레기 비트를 지워야 함(안 하면 없는 시간대에 "빈자리" 오탐).
2. **바닥이 아니라 '크레인 그림자' 격자를 반전해야.** 바닥만 비었다고 크레인 진입 가능
   아님(위 기둥이 막혔을 수 있음). → shadow 누적 격자를 반전해야 "크레인까지 되는 자리"가
   나온다.
3. **"기하급수적 감소"는 과장.** 발자국을 여전히 위치마다 슬라이드하며 AND해야 하므로
   상수배·벡터화 이득이지 복잡도 클래스가 바뀌진 않는다. (그래도 pricing 내부 후보
   필터로는 충분히 값어치 있음.)

## 종합 — 어디에 어떻게 붙일까

| 팁 | 역할 | 우리 문제 적용 |
|----|------|----------------|
| 1 (시간 uint64+Numba) | 고속 feasibility | **열생성 pricing**의 실행가능성 검사. 단 다중워드(지평>64) + 레이어축 |
| 2 (크레인 선형화) | MIP 제약 | **제안식은 틀림.** shadow-augmented set-packing(§3.3)로 대체 |
| 3 (~Grid 스카이라인) | 후보 열거 | pricing/휴리스틱 후보 필터. 단 지평마스크 + shadow격자 반전 |

즉 이상적 구조: **MIP(집합분할, 크레인=shadow set-packing) = 최적성 담당**,
그 안에 **팁1·3의 비트보드 pricing 엔진 = 좋은 열 초고속 공급**. 두 층을 분리하면
"수리계획 최적성"과 "비트 연산 속도"를 동시에 얻는다 — 팁의 방향성은 옳고, 팁2의
식만 바로잡으면 된다.
